- **quitting no longer has to kill every live session** — a new 5th quit-dialog choice, "leave them running," hands each live session's pty master file descriptor off to a small detached `ptyKeeper.ts` helper process instead of signaling it, so the underlying `claude` CLI survives the app quitting entirely and reattaches automatically (backlog + live stream) on the next launch, ahead of `sessionRespawn.ts`'s existing `claude --resume` path (which it falls through to unchanged if the keeper's already gone — process finished naturally while detached, or never existed for that session). Root cause of why this needed a real subsystem rather than just skipping `killAll()`: closing the pty master kills the terminal itself (writes start failing), not just delivers a signal — even a child explicitly wrapped to ignore SIGHUP still died within ~1s of its pty-owning parent exiting in testing. Only a separate process holding its own open reference to the same master keeps the underlying open-file-description alive, confirmed by direct experiment (fd handoff via `ELECTRON_RUN_AS_NODE`-spawned, `detached`, fd-inherited child) — re-verified against the real Electron binary under production conditions, including surviving a 6s idle gap with no pty output. `PtySession.proc` narrowed to a `PtyLike` interface so a `KeeperClient` socket adapter can stand in for a real `pty.IPty` transparently; a live reader's own `pause()`/`resume()` guards the fd handoff against a dual-reader race. Live resize while detached is a known V1 gap (reattached terminal keeps its last size) — reaching node-pty's internal native resize binding from a standalone process wasn't reachable without more risk than it was worth for v1. Claude Sonnet subagent, orchestrator design-validated by direct experiment before implementation, advisor-reviewed, reviewed/merged by the orchestrator

- **spawned agents could silently lose transcript persistence and get their session identity misattributed, if pokeharness itself was launched from inside an existing Claude Code session** (e.g. running `npm run dev` from a Claude Code terminal) — `buildBaseEnv` spread the entire Electron main process `process.env` into every spawned CLI's env with no scrubbing, so Claude Code session-identity markers (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_PID`, and others) leaked straight through. `CLAUDE_CODE_CHILD_SESSION` made the CLI wrongly treat every spawned agent — always meant to be a real, resumable top-level session — as a nested child/subagent and disable transcript saving for it; `CLAUDE_CODE_SESSION_ID` could get latched as the spawned agent's own session/CCR identity. First pass at the fix stripped only the child-session marker and force-set `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1`, but an advisor review caught that forcing persistence on isn't inert — it inherits down to every child process a spawned agent creates (e.g. a Bash-tool `claude -p ...` call), forcing persistence on *genuine* nested child sessions too and defeating the CLI's own marker for the whole subtree. Replaced with `CLEAN_LAUNCH_ENV_DENYLIST`, mirroring the Claude Code CLI's own denylist for launching a clean top-level session from inside an existing one; `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_USE_*` are left untouched since other pokeharness code depends on them passing through. Claude Sonnet subagent, advisor-reviewed, reviewed/merged by the orchestrator

- **a dev run (`npm run dev`) showed the same conversations as the packaged app** — `app.setName('Pokéharness')` was unconditional, so `app.getPath('userData')` (which every session/settings/cache/hooks-socket path derives from) resolved to the exact same directory whether the app was running from source or packaged, meaning a dev run read and could write the user's real production session state. Dev now resolves to `'Pokéharness Dev'` (`app.isPackaged` gates it), giving it a fully separate `userData` dir — separate `sessions.json`, `app-settings.json`, caches, and `hooks.sock` — so a fresh dev launch now shows the real first-run onboarding instead of live production data. - **Electron bumped 32.2.0 → 44.2.0** — an ~11-major-behind pin found by a perf/architecture audit, closed via twelve sequential one-major-at-a-time hops (32→33→34→…→44) rather than one large jump, each checked against Electron's own version-specific breaking-changes doc, rebuilt (`node-pty`'s native module via the existing `electron-rebuild` postinstall), typechecked, and built before merging. Across all twelve hops, no source code changes were needed — every flagged breaking API (clipboard-paste/renderer-clipboard removal, `WebFrameMain` detached-instance behavior, `protocol.registerFileProtocol`, utility-process `login`/`isUnityRunning`, `textured`/frameless-window changes, `session`/`WebRequestFilter`/`NativeImage` deprecations, ANGLE static linking, macOS 11/12 support drops, Windows ia32/Linux armv7l prebuilt discontinuation, and more) turned out unused by this codebase, which is mac arm64-only. Two purely cosmetic behavior changes worth knowing about: macOS notifications now route through `UNNotification` (app already ad-hoc code-signs; worth confirming notifications still fire in a packaged build) and the folder-picker dialog's default directory is now Downloads instead of the OS default (no `defaultPath` was set, so Electron's own new default applies). `node-pty` and `electron-builder` needed no accompanying version bumps at any hop. Claude Sonnet subagent (one dispatch per hop), reviewed/merged by the orchestrator
- **PTY session cap, lazier startup, and event-driven transcript watching** — three fixes from the same audit. `PtyManager` had no limit on concurrent `node-pty` child processes, so a runaway spawn loop could exhaust OS file descriptors/PTYs; capped at 64 concurrent sessions, failing clearly (`{ok:false, error}`, matching `spawn()`'s existing convention) rather than degrading silently. `createWindow()` previously ran only after the entire boot init chain (hook bridge, watcher starts, settings loads, usage-service init, harness-home setup, diagnostics) had awaited to completion; it now fires as soon as theme/usage-snapshot/harness-home are ready, letting the renderer bundle load concurrently with the rest of boot instead of serially after it. `costWatcher`/`taskNotificationWatcher` switched their transcript reads from fixed-interval polling (5s/2s) to primarily `fs.watch`-triggered reads, keeping a slower interval (30s) as a fallback safety net for `fs.watch`'s known missed-event cases. An advisor review before merge caught two real bugs in the first pass: the startup reorder left two `await`s (harness-home resolution) between `createWindow()` and a promise reassignment the renderer's first-mount IPC calls race against, which could have handed the renderer stale/placeholder restore data on a slow (e.g. network-mounted) harness-home path; and the watcher's `fs.watch` setup had no retry path, so a transcript that didn't exist yet at registration time got permanently stuck on the slow fallback poll instead of picking up the fast path once the file appeared. Both fixed before merge. Claude Sonnet subagent, advisor-reviewed, reviewed/merged by the orchestrator

- **an idle garden with many open sessions could render at the full ~60fps tick rate forever instead of downshifting** (GitHub #33) — `WalkerSprite`'s bob for levitate/fly locomotion Pokemon (`BOB[...].whileStill`) marked the scene dirty unconditionally on every ticker frame even while the walker wasn't moving at all, since "floating Pokemon never stop bobbing" was true regardless of activity. `renderDirty.ts` is one shared, garden-wide flag, so a single such walker anywhere in the garden — a live session's own Pokemon, or an un-despawned roaming/retired subagent battler left over from an earlier fight — was enough to pin `app.render()` at full rate for the whole scene forever, with more accumulated sessions/battles making that more likely to happen. - **a poisoned battle sub could crash every render tick, forever, once triggered — independent of window visibility or garden-idle state** (GitHub #31, found while doing #6's live measurement pass) — `harness.log` showed one battle throwing the same `TypeError` inside `WalkerSprite.applyTransform` 34,295 times in 7.5 minutes (~76/sec). Root cause: `destroyBattle` is the one `Battler`-destroy call site that doesn't clear `pb.subs` itself — it relies on its caller (`forceEnd`) to drop the whole `ParentBattle` afterward. `forceEnd` called `destroyBattle` *before* deleting from `this.battles`, and `destroyBattle`'s per-sub loop calls a synchronous store write mid-loop that GardenScene's reconcile reacts to immediately — including, for a session already gone from `sessions` but not yet from `runtimes`, a **re-entrant `forceEnd` for the same parent**, recursing into `destroyBattle` again on the same never-cleared `pb.subs`. Unbounded recursion to a `RangeError` that only reached a bare `console.error` (never captured by `harness.log`) and unwound without ever reaching the delete — leaving the exact zombie state observed: the parent still tracked, its one sub's `Battler` genuinely destroyed but still sitting in `pb.subs`, crashing the next tick's unconditional `update()` call forever. Fixed at the source (`forceEnd` now deletes before destroying; `destroyBattle` snapshots-and-clears `pb.subs`/`pb.waveRing` before its own loop), backed by a `dropDestroyedSubs` sweep mirroring `battleFx.ts`'s existing three-layer defense for the identical failure shape on the FX-tick path. An advisor review of the first implementation pass caught that its sweep ran store side effects before its own array reassignment committed — which would have silently turned the crash from a `TypeError` into an equally-infinite `RangeError` loop instead of actually stopping it; fixed before merge. Claude Sonnet subagent, advisor-reviewed, reviewed/merged by the orchestrator
